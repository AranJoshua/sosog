# SOSOG Technical Plan — Full Reasoning

This is the long version. `AGENTS.md` gives Codex the decisions it needs to start building. This document is where the reasoning behind each decision lives, so a decision that looks wrong once building actually starts can be caught and flagged before building starts instead of after.

## 1. Is the Google Sheet actually the right data source?

Short answer: yes, with a validation layer in front of it. Here's the full case.

### Why the Sheet stays

The client team already maintains the checklist sheet, and they will keep editing it after the defense, since nobody hands a non-technical BSCE team a git workflow and expects them to keep using it. Any data source that requires the client to learn a new tool has a real chance of getting abandoned within a semester, at which point the site stops reflecting reality. A spreadsheet they already know how to use is the option most likely to actually stay updated.

### Where a spreadsheet genuinely breaks things

A raw, unvalidated read of the Sheet is fragile in a few specific ways worth naming, since "we're using Sheets" and "we're using Sheets safely" are different projects.

Free-text fields invite inconsistency. Nothing stops one row from writing "Sorsogon City" and another from writing "Sorsogon" or "Sorsogon Cty," and a build that groups structures by municipality will silently split what should be one group into three.

Coordinates typed by hand are a common failure point. One row might paste "12.9705, 124.0067" into a single cell, another might split latitude and longitude into two columns, and another might round-trip through a phone's GPS app and pick up stray characters. A build script that expects a clean number will either crash or, worse, quietly render a pin in the wrong place.

Column reordering or renaming is the most dangerous failure mode, because it's invisible until something downstream breaks. If someone inserts a column, retitles a header, or merges two cells while cleaning up the sheet, a script reading by column position or by an exact header string can start pulling the wrong field into the wrong slot without throwing any error at all.

That risk splits into two cases worth telling apart, since only one of them announces itself. A renamed or vanished header on a structural field, name, municipality, or coordinates, still trips the loud build failure the two-tier system is built around, a missing structural value fails by design whether it's missing because a cell is blank or because the whole column disappeared. A renamed or merged header on a content field is the real gap: content fields degrade to a silent "coming soon" by design, so if the "Technical Description" header gets retitled or merged away, every one of the 45 rows loses that field at once with no error anywhere, indistinguishable from ordinary in-progress editing until someone happens to notice the whole column went blank. Closing that takes two cheap things, not one. The sync script should check that every expected column header exists in the sheet at all before it processes a single row, failing the whole build by column name if one's missing, and the instructions handed to the client team should ask them not to rename or reorder the header row in the first place. Neither replaces the other: the header check catches a corruption the client didn't mean to make, and the plain-language ask reduces how often it happens at all.

Row-level gaps still need a plan even though the build won't start until all the structures' content is complete. The plan for gaps is entirely about what happens after that, once the client keeps editing the live Sheet: a new structure gets added before all its content is written, or an existing entry gets a field cleared mid-edit. The schema needs two tiers to handle that safely, not one. A small set of structural fields, name, municipality (against a fixed valid list), and coordinates, must exist and be well-formed for a row to render at all; without them there's no pin to place and no page to build, so a blank or malformed value there fails the build loudly, naming the row and field, rather than deploying a broken pin or a nameless page. Everything else, history, technical description, and the feature story, is content that can legitimately be mid-progress on any given day post-launch: a missing one of these doesn't fail the whole nightly build for every other structure, it renders that specific section as an explicit "coming soon" state on that one structure's page instead. That's the entire point of the placeholder, to protect ongoing edits after launch from taking the whole site's nightly sync hostage over one unfinished paragraph, not a mechanism for launching before the current 45 are complete. Before the build starts, every one of those content fields should already be filled in for all the structures, so "coming soon" should never actually appear on day one. It only starts doing work the first time the client adds a 46th structure or leaves a field blank while still writing it.

### What was considered instead, and why it lost

A headless CMS (Sanity, Contentful, or a git-based option like Decap CMS) gives real schema validation and a proper media library out of the box. It loses on the same point that makes Sheets attractive: it's a new interface for a team that's mid-thesis and already using something else. Decap CMS in particular stores content as files in your git repo, which is the cleanest technical fit but still assumes editors are comfortable with a GitHub-backed workflow, which this team isn't. Free tiers on hosted CMS options also tend to cap image storage or API calls in ways that are easy to hit across 45 records with several photos each.

Flat markdown or JSON files committed straight to the repo are the most bulletproof option for build reliability, since there's no runtime fetch, no API quota, and git itself becomes the audit trail. This loses for the same maintainability reason as a headless CMS: editing a markdown file with YAML frontmatter through GitHub's web editor is a worse experience than a spreadsheet for someone who's never done it, and it's the option most likely to quietly stop getting updated once the client's team graduates.

A lightweight database (Supabase, Turso, or similar free-tier hosted options) is overkill for a site with no accounts, no real-time data, and no dynamic queries, everything here can be computed once at build time and served as static files. It also introduces a new failure mode this project doesn't need: most free-tier hosted databases pause or sleep a project after a stretch of inactivity, which is a real risk for a site nobody is actively paying for or administering a year from now.

### The actual recommendation

Keep the Google Sheet as the source of truth, but never let the site read it directly at request time. Instead, a build-time script fetches the sheet, validates every row against a strict schema (required fields, a fixed list of valid municipality names instead of free text, a coordinate format check), and only then writes a normalized JSON file per structure. A row that fails validation on a structural field, a missing or malformed name, municipality, or coordinate, should fail the build loudly, with the specific row and field named in the error, rather than either crashing opaquely or publishing broken data. A row that's simply missing a content field that hasn't been written yet, history, technical description, or the feature story, should pass validation and render that section as an explicit "coming soon" state instead, so one unfinished structure never blocks the nightly deploy for the others. That two-tier split is what turns "a spreadsheet a non-technical team edits" from a liability into a genuinely workable content system, and the "coming soon" state exists purely to protect that ongoing post-launch editing, not to let the initial build ship with anything unfinished.

Two mechanical choices remain, both cheap to set up. For actually pulling the data, publishing the relevant sheet tabs "to the web" as CSV (File, Share, Publish to web) gives a public, no-authentication URL that always reflects the latest saved version, which is the simplest possible pipeline and costs nothing to maintain. The trade-off is that anyone with the link can view that CSV, which is a non-issue for the content itself, but it's worth being precise about what "the content" means here: Google's publish-to-web is scoped per tab, not per column or range, so it publishes everything in whichever tab it's pointed at, not just the fields the site's schema actually uses. A "checklist sheet" a client team edits directly very plausibly grows workflow columns over time, who's assigned, status, internal remarks, that were never meant to be public. If those end up living in the same tab as the public content fields, publishing that tab publishes them too, with no way to publish just a subset of its columns. The fix costs nothing: either confirm directly with the client that the tab they edit contains no non-public columns before publishing it, or add a dedicated tab that references just the schema's fields with simple cell formulas and publish that clean tab instead, leaving their working tab, extra columns and all, unpublished. The more locked-down alternative is the Sheets API with a service account key, which respects normal sharing permissions instead of requiring a public link, at the cost of one extra setup step (creating a Google Cloud service account) that has to happen once and then gets forgotten. Given the content isn't sensitive, publish-to-web CSV is the simpler default, worth revisiting only if the client ever wants the raw sheet itself kept private, or if the column-scope check above turns up something that shouldn't go public. One caveat worth knowing ahead of time rather than discovering mid-debug: a published sheet doesn't update at that URL instantly, Google's own propagation lag runs anywhere from a few minutes to a couple of hours, so an edit made right before the nightly sync fires can land in the following night's build instead of that night's. For a once-a-day sync this is a non-issue in practice, but it's worth knowing so nobody spends an hour debugging a sync that worked correctly and just ran a few minutes too early.

The coordinate format itself is worth pinning down concretely rather than leaving as "a coordinate format check" in the abstract, since the client-facing instructions are exactly where this plan's own warning about ambiguity applies to itself. Standardize on one column, a single cell holding `latitude, longitude` as plain decimal degrees (the same shape as the "12.9705, 124.0067" example used earlier in this document), rather than splitting latitude and longitude across two columns. One column is one thing to get wrong instead of two, and the validation regex is simple: two decimal numbers separated by a comma, latitude between -90 and 90, longitude between -180 and 180. Whatever the choice, it belongs in the actual written instructions handed to the client team, not just in this document.

The other gap worth closing is what happens after launch. Nobody on the client's team should need to ping the dev team every time they update a row. The nightly rebuild mechanism that closes that gap is described in full in Section 3, since it's really a deployment-platform question, not a data-pipeline one, and Section 3 has since been revised on exactly that point.

### A note on repo visibility

The repo should still be public. GitHub's free secret-scanning push protection blocks a push outright if it contains a recognizable secret pattern, a Google service account key, a common API token format, before it reaches the remote, and on a personal GitHub account that protection is only free for public repositories, it's a paid add-on for private ones. That's a backstop, not a replacement, for keeping every credential in environment variables and never in the repo, but for a project built and iterated on quickly by an AI agent, having it live for free costs nothing and catches a real class of mistake. There's no GitHub Actions workflow anywhere in this design (see Section 3), so there's no scheduled-workflow dormancy concern on either hosting platform either.

## 2. Full stack decision

### What this project actually needs

Restating the shape of the problem keeps the stack choice honest. This is a content-heavy site, the large majority of it static text and images that don't change per visitor. It has exactly one genuinely interactive piece, the map. It has no accounts, no logins, and no payments anywhere in the spec, so nothing here needs a server that runs per-request logic. It needs to build fast and often, since a heavily iterated build over three weeks could easily produce dozens of deploys. And every piece of the stack has to be free indefinitely, not free for a trial period.

### Framework

Four real options were on the table.

Next.js with static export is the most common pick and the one an AI coding agent has the most training data on, which matters for how many bugs show up during an 18-day build. It works fine as a static site once `output: 'export'` is set, but it drags along React's client-side hydration model even for pages that don't need any interactivity, and `next/image` specifically breaks on a pure static export unless it's set to unoptimized or wired to a custom loader, a real trap worth knowing about before it eats a day of debugging.

Astro was built for close to this exact project shape: a content-heavy site with isolated islands of interactivity. It ships zero JavaScript by default and only hydrates the specific component that needs it, which here is just the map, everything else renders as plain HTML. Astro's content collections come with built-in Zod schema validation, which is the same validation layer the Sheet plan above calls for, so adopting Astro doesn't add a new tool for that job, it already has one built in. The one honest trade-off is that Astro has less presence in an AI agent's training data than Next.js or React, so Codex may occasionally reach for a React-flavored pattern that needs correcting. That risk is real but manageable, Astro is well documented and stable, not an obscure or shrinking framework, and the architectural fit is strong enough to be worth that small friction. This fit has also strengthened since this plan was first drafted: Cloudflare acquired the team behind Astro in January 2026, and Astro's own deployment docs now steer new projects toward Cloudflare Workers, the platform this plan lands on in Section 3 for independent reasons.

One more decision worth naming directly rather than leaving implicit: target whatever a fresh scaffold gives you as current stable, don't deliberately pin to an older major out of caution. When this plan was first drafted, a fresh scaffold installed Astro 6, and pinning to 6 rather than fighting its defaults back to 5 was the right call. Astro has since shipped 7 (released July 2026, a Rust-compiler and Vite-8/Rolldown infrastructure release), so a fresh scaffold today installs 7, not 6. The Content Layer API changes that mattered for 6, the move to `src/content.config.ts`, and Zod schemas running on Zod 4 with stricter default-value rules, carry forward unchanged into 7; Astro 7 didn't reintroduce the legacy v4-style fallback that 6 dropped. Naming these directly in AGENTS.md, so Codex doesn't have to rediscover them through trial and error, is cheaper than downgrading a framework for a problem staying current doesn't actually create. The general principle from the earlier draft still holds, just pointed at a newer number: don't fight the tool's own defaults without a concrete reason to.

A third applicable change is easy to miss because it doesn't fail the build: `z` exported from `astro:content` (and its alias `astro:schema`) has been deprecated since Astro 6 in favor of importing it from `astro/zod`. `import { z, defineCollection } from 'astro:content'` was the standard, idiomatic Astro 5 pattern, so it's almost certainly the single most common Astro import in Codex's training data, which makes it the most likely of these breaking changes to actually get written. Because it's a deprecation warning rather than a hard removal, it won't announce itself the way the others do, an agent could ship the whole build on the deprecated import and nothing downstream would flag it. It costs one line in AGENTS.md to close, so it's worth naming alongside the other two rather than leaving it as a gap.

A fourth thing worth flagging honestly rather than pretending it's settled: the specific Tailwind-integration bug this plan originally cited (a rolldown/oxc resolver failure in `@tailwindcss/vite` on Astro 6.2.x) turned out not to be a fixed, one-time bug at all. Evidence since then shows the same class of resolver bug moving between the `@tailwindcss/vite` path and the `@tailwindcss/postcss` fallback path across successive Astro and Vite releases, breaking whichever one isn't currently being watched. The right instruction here isn't "use PostCSS, it's the known-good workaround," it's "run a real build with a trivial Tailwind stylesheet on Day 1 and see which path actually works on the exact versions you land on," which is what the revised AGENTS.md now says. This is the one place in this stack where an AI agent's training data is more likely to reproduce a broken setup than a working one, and that stays true regardless of which specific version is current when you read this.

Eleventy (11ty) is a mature, JS-based static site generator with the same zero-JS-by-default philosophy as Astro. It loses to Astro on one specific point that matters a lot here: it has no built-in way to mount a component (React, Preact, or otherwise) as an isolated interactive island, that would need to be wired up by hand. Since the map is the single most complex piece of this build, Astro's native island support is worth more than Eleventy's slightly simpler mental model elsewhere.

A plain Vite single-page app was ruled out early. It would need extra tooling bolted on just to get the prerendering and per-page HTML that Astro or Next give for free, and a content site benefits from that prerendering both for fast initial mobile load and for pages actually existing as real HTML rather than being assembled client-side after the fact.

Astro is the pick.

### Backend

None needed, and none should be added. A backend earns its cost when something has to run logic per request, authenticate a user, or write data back from a client action. Nothing in the SOSOG spec does any of that. Structure data gets fetched, validated, and baked into static files at build time, not queried live. Adding a backend here would mean paying (in complexity, and eventually in money) to solve a problem that doesn't exist in this project.

### Database

Also not needed, beyond the generated JSON files that live in the repo as a build artifact. A real database is worth its overhead when data changes per-request or needs relational queries across a large, growing dataset. Forty-five structures with a fixed shape don't need that, and a database would add a runtime dependency and a possible point of failure (a sleeping free-tier instance, a connection limit) to a site that's supposed to keep working with nobody actively maintaining it.

### The map component

The spec calls for a stylized illustrated province map with clickable pins and a simple highlight, explicitly not a survey-accurate, real-tile map. That rules out Leaflet or Mapbox GL as the base layer, both are built for real geographic tiles and bring meaningful bundle weight and, for Mapbox specifically, an API key tied to a metered free tier, none of which this project needs. The right-sized approach is static SVG boundary paths rendered inside one small interactive component, a Preact or React island mounted only on the map page, handling click state, the highlight effect, and the pin popups. Boundary sourcing turned out to be exactly the same-day scripted job this plan expected, not hand-tracing from a blank reference. The actual source used is the Philippine Statistics Authority's PSGC-based administrative boundary data, pulled via faeldon/philippines-json-maps (MIT licensed, itself derived from PSA/PSGC shapefiles via altcoder/philippines-psgc-shapefiles), already mapshaper-simplified upstream at a resolution well suited to a stylized map, 336 total points across all 15 of Sorsogon's municipalities and city. The real bounding box computed from that data turned out meaningfully wider on the west side than an earlier placeholder guess, confirming it was worth sourcing the real geometry before building the pin-projection math around an assumption. `src/components/map/boundaries.ts` and `boundaries.svg` carry the result; Map.tsx projects structure pins onto the same coordinate space using the same `BOUNDS` constant, so pins and boundaries can't drift apart. PSA's terms ask for a source credit, which the about page now carries. Everything else on the site stays untouched by that component's JavaScript.

The pin data itself, name, municipality, and coordinates for each of the 45 structures, should be a build-time prop passed straight into the Map island, not something it fetches at runtime. An earlier draft of this plan and of AGENTS.md carved out an exception here, "nothing fetches data client-side except the map," but that exception was never actually load-bearing, it's simply the one place a runtime fetch was left in by default. At this scale the whole dataset is a few kilobytes, name, municipality, and a lat/lng pair per structure, trivial to serialize into the island's props the same way every other page already gets its content from the build-time collection. Doing that removes a runtime network dependency, one fetch call that could be slow, could fail, or could simply be one more thing to debug, for no cost at all, and it makes the "nothing fetches client-side" rule actually true without an asterisk instead of true with one.

### Photos

The guide's existing data flow points at Google Drive links for photos. Hotlinking directly from Drive in production is a known bad practice, Drive's direct-link URLs are rate-limited, sometimes serve a low-resolution thumbnail instead of the real image, and can break without warning under real traffic. The fix is still a sync step: `scripts/sync-photos.ts` pulls each photo from its Drive link, resizes and compresses it. What changes is the destination. It writes the result straight into `public/` as part of the same build step that generates the structure JSON from the Sheet, and that write is never committed to the repo.

Writing straight into `public/` means these photos skip Astro's own image pipeline, so nothing generates a responsive `srcset` or infers width and height the way it would for an image Astro optimizes itself. `sync-photos.ts` should produce two variants per photo instead of one, a small thumbnail for the photo feed and structure cards and a larger version for the detail page, and every template referencing a synced photo should set explicit width, height, and `loading="lazy"` by hand. This is the part of the mobile-performance target in Testing that the pipeline is actually responsible for; without it, the Lighthouse pass in section 4 is the check most likely to fail late.

Drive access should be a Google Cloud service account added as a viewer on the client's Drive folder, not an OAuth user token. The service account key doesn't expire from disuse the way an OAuth refresh token can, which matters for the same reason the deploy scheduling does: nobody's going to be around to re-authenticate anything a year from now.

One correction worth making here: Cloudflare's build environment checks out a clean copy of the repo for every build on both Pages and Workers, so a comparison against "what's already in `public/`" has nothing to compare against, `public/` never carries anything over from the previous build. If a skip-unchanged step is worth having, the manifest it checks against needs to live somewhere the build cache actually persists, and for an Astro project that's `node_modules/.astro`, and only once build caching is turned on for the project (this setting's exact location moved when this plan shifted from Pages to Workers Builds, see Section 3, so check the current dashboard rather than assume the old Pages path). The sync script can write a small JSON manifest there mapping each structure's Drive file ID and modified time to the already-processed file, and skip reprocessing anything that still matches. Without that, every nightly sync reprocesses every photo from scratch. At roughly 45 structures with a handful of compressed photos each, that's very likely still comfortably inside the build timeout on its own, so this isn't a launch blocker, but the claim should be about "reprocessing everything is cheap enough at this scale," not "the pipeline skips unchanged photos," unless the manifest actually gets built.

Cloudflare R2 was the original plan for serving those images, but it's solving a problem this project doesn't have. At roughly 45 structures with a handful of compressed photos each, the site sits at a few hundred files total, nowhere near the 20,000-file or 25 MiB-per-file caps that apply to static assets on either Pages or Workers, so a separate object storage service earns nothing here. R2's real value, avoiding that file cap, no egress fees, updating images without a full rebuild, doesn't apply at this scale since static asset serving is already unlimited on the free plan and the nightly job forces a full rebuild regardless. Committing the compressed photos straight into git was the obvious alternative, but it has its own cost the R2 plan was trying to avoid: nightly re-syncs would keep dumping new image blobs into git history indefinitely, growing the repo forever. Writing them into `public/` at build time sidesteps both problems. No bucket, no access keys, no CORS setup, and no growing repo, and one less service to keep credentials for.

### Styling

Tailwind CSS. It's free, has essentially universal presence in an agent's training data (another point in favor of fewer build-time errors), purges down to a small final CSS file, and its responsive utility classes handle fluid, screen-adaptive layouts across arbitrary screen sizes, there's no need to hand-write separate desktop and mobile stylesheets. The one current exception to that training-data advantage, the Tailwind-integration bug that keeps moving between its two setup paths across Astro and Vite releases, is covered above under Framework and in AGENTS.md; treat it as a Day-1 thing to verify against whatever versions you actually land on, not a settled fact from an earlier version.

## 3. Deployment specifics

The site deploys to Cloudflare Workers, using Workers' static-assets feature, not Cloudflare Pages. This is a reversal from an earlier version of this plan, and it's worth being direct about why, since the earlier version reasoned through this same question and landed on Pages.

### Why this plan originally chose Pages, and why that reasoning has expired

An earlier draft moved the site's hosting from Pages to Workers, then a later pass corrected that move, on the grounds that the claimed unlock, Workers Builds gaining Deploy Hooks, wasn't actually a reason to leave Pages, since Pages already had Deploy Hooks since August 2021 and the nightly-rebuild mechanism (a Cron Worker calling a Deploy Hook) works identically on both platforms either way. That correction was right on its own terms, and it's still true: the nightly job doesn't care which platform hosts the site. But that same pass weighed one more factor and came out on the side of staying on Pages: Cloudflare's documentation was starting to steer new projects toward Workers, a signal tied to Cloudflare's January 2026 acquisition of the Astro team, but Workers' static-assets deploy path was, at the time, newer and less battle-tested than Pages, which mattered for an 18-day, zero-slack, AI-agent-built site. Weighed against each other, the better-documented platform won, and the plan stayed on Pages.

That specific premise, Workers' static-assets path being newer and less documented, no longer holds. Workers reached full feature parity with Pages for static assets, SSR, and custom domains by March 2026. Astro's own official deployment guide now states plainly that Cloudflare recommends using Cloudflare Workers for new projects, with Pages positioned as the option for existing projects rather than new ones. Workers Builds, the git-connected CI/CD for Workers, is as turnkey now as Pages' git integration always was, push to `main`, Cloudflare detects the framework, runs the build, deploys the output, no separate configuration step needed for that basic flow. And Workers Builds picked up Deploy Hooks of its own on April 1, 2026, the identical POST-to-rebuild mechanism Pages has had since 2021, so the nightly-rebuild design in this plan carries over to Workers completely unchanged, just pointed at a different platform's hook URL.

Put differently: the earlier correction was right that Deploy Hooks were never a reason to prefer Workers over Pages, since both have them. But by the same logic, Deploy Hooks are no longer a reason to prefer Pages over Workers either, since both still have them. With that consideration neutralized on both sides, the deciding factor becomes whichever platform is currently the better-supported, more-current default, and that's now Workers, for reasons that didn't exist when this plan first weighed the question. There's also a small practical benefit specific to this project: `cron-worker/` already needs Wrangler regardless of which platform hosts the main site, so deploying the main site as a Worker too means one deploy toolchain for the whole project instead of two.

### What actually changes in practice

Very little, mechanically. The main site becomes a Worker with a static-assets configuration (`wrangler.jsonc` with an `assets` block pointing at `./dist`, no `main` entry point needed since there's no server-side code) instead of a Pages project with an auto-detected framework preset. It deploys via Workers Builds' git integration instead of Pages' git integration, functionally the same push-to-deploy flow. It ships on a `*.workers.dev` subdomain instead of `*.pages.dev`. Secrets move from Pages' environment-variables UI to Wrangler secrets (`wrangler secret put`), which is if anything a small security improvement since Wrangler secrets aren't visible in the dashboard after they're set. The free-tier numbers that matter for this project are comparable or better: static asset requests remain free and unlimited, the file caps stay at 20,000 files and 25 MiB per file, and the build allowance moves from Pages' 500-builds-a-month cap to Workers Builds' 3,000-build-minutes-a-month cap, which for a small static-site build measured in low single-digit minutes per build is materially roomier than it sounds, and not something a normal iteration pace over the remaining build window will come close to.

The site ships on the free `*.workers.dev` subdomain. No custom domain is being purchased, which keeps the project budget entirely one-time rather than exposing it to a recurring annual renewal cost that would otherwise be the one line item nobody's tracking a year from now.

The nightly job doesn't change shape at all: a small, dedicated Cloudflare Worker on its own Cron Trigger, whose only job is to `POST` to the main site Worker's own Deploy Hook once a day, no GitHub Actions anywhere in that path. A bad edit still fails the actual build loudly and keeps the previous version live; the sync script itself, not an external CI step, is what emails the client and dev team when that happens.

## 4. Testing and QA approach

There's no user-facing logic to unit test in the traditional sense, so "testing" here means a few concrete, automatable checks rather than a full test suite.

Row validation is the first line of defense: `sync-sheet.ts` runs the same structural checks against every row as part of `npm run build` itself and fails loudly on any row that doesn't match the schema, naming the row and field (see Section 3's revision of the deployment path for why this no longer sits in a separate CI step). `npm run validate:data` shares that validation logic and is still worth running locally before pushing, but it's a convenience check, not a build gate.

A link and image checker, run against the built output, catches broken internal links and missing images before they reach production, both of which are easy to introduce across 45 near-identical structure pages.

A basic mobile performance pass (Lighthouse or similar) against the built site checks that the "polished on mobile" bar is actually being met, not just assumed, since that's the requirement most likely to quietly slip during a fast build.

Before calling it done, a manual pass through every page across a range of screen sizes, laptop as the primary target, checking every structure detail page loads its photos and text, every map pin opens its correct popup, and the feature story template renders correctly with each story's swapped elements, closes the loop the automated checks can't fully cover. That same pass should confirm no page shows a "coming soon" state anywhere, since the placeholder exists only to protect edits made after launch and shouldn't appear in the launch build itself.
