# SOSOG — Agent Instructions

> New to this project? Read `PROJECT_CONTEXT.md` first for the full picture (who, what, status, decisions, open items), then this file for the working rules.

SOSOG documents the historical structures of Sorsogon province (41 in the client's sheet as of 31 October 2026, with more possible) for a BSCE course project. It is a browsing-only informational site: a Netflix-style home page with an Explore carousel of municipalities, an interactive province map with clickable structure pins and popups, individual structure pages (History tab by default, plus Feature Story and Technical Description), index pages for Technical Description, History, and Feature Stories, a Glimpse of Sorsogon photo feed, and an About Us page. There are no accounts, logins, comments, or submissions anywhere in the spec, and none should be added. The client's website guide (`WEBSITE_GUIDE_SOSOG_BSCE`) is the source of truth for layout, palette, and typography.

## Stack and why

| Piece | Choice | One-line reason |
|---|---|---|
| Framework | Astro, static output, current stable (7.x as of this writing) | Content-heavy site with one interactive part (the map); Astro ships zero JS by default and hydrates only what needs it |
| Styling | Tailwind CSS | Fast to build with, purges to a small CSS file, its utility classes handle fluid, screen-adaptive layouts without hand-written breakpoints |
| Structure data | Client's Google Sheet, fetched and validated at build time | The client team already maintains it and will keep editing it after the defense |
| Photos | Prepared locally with `scripts/sosog_prep_photos.py` (HEIC, DNG, and JPG originals to web-size JPEGs with all metadata stripped), then committed to the repo in `public/structures/` and `public/glimpse/` | Decided October 2026 in place of a Drive sync: photos rarely change after launch, about 40 MB in total sits far under Cloudflare's static-asset limits (20,000 files, 25 MiB each), and it removes the Drive service-account key and its failure modes. Sheet text edits still update nightly |
| Map rendering | Static SVG boundary paths, one small JS island for interactivity | The spec calls for a stylized map, not a real-tile map, so a mapping library like Leaflet is unnecessary weight |
| Hosting | Cloudflare Workers, static assets, deployed via Workers Builds | Cloudflare's own docs now recommend Workers over Pages for new projects, and Workers reached full feature parity with Pages for static sites in March 2026; Deploy Hooks (a small Cron-triggered Worker can call one directly) exist on Workers Builds too, so the nightly-rebuild mechanism is unchanged either way |

Full reasoning behind every choice above, plus the Google Sheet evaluation and the Pages-vs-Workers call, lives in `sosog-tech-plan.md`. Read that file if a decision here seems worth reconsidering, don't relitigate it from scratch.

## Framework version note

This project targets whatever Astro ships as current stable, which is the 7.x line as of this writing (Astro 7.0 released July 2026, an infrastructure release: Rust-rewritten `.astro` compiler, a Rust Markdown pipeline, and a bundler switch to Vite 8 with Rolldown). Don't deliberately downgrade to 5 or 6. Astro moves fast; if a fresh `npm create astro@latest` on the day you actually scaffold installs something newer than 7, that's fine, stay on whatever it gives you rather than pinning backward, and skim that version's own upgrade notes for anything not covered below.

The Content Layer API rules below were introduced in Astro 5 and made mandatory in Astro 6, and they carry forward unchanged into 7, so they're still the right things to get right from the start. Content collections must use `src/content.config.ts` with the Content Layer API (a `loader`, no `type: 'content'` or `type: 'data'`), and Zod schemas run on Zod 4, where a `.default()` on a transformed field has to match the transformed output type, not the raw input type. A `LegacyContentConfigError`, a `ContentCollectionMissingALoaderError`, or a Zod default that silently doesn't apply are all this. The actual failure mode to watch for is training data reaching for the legacy v4-style fallback, not the current major version itself.

A second rule applies too: `z` exported from `astro:content` (and `astro:schema`) has been deprecated since Astro 6 in favor of importing it from `astro/zod`. `import { z, defineCollection } from 'astro:content'` was the standard Astro 5 pattern, so it's the single most likely legacy import an agent reaches for out of habit. It still works as a deprecation warning rather than a hard failure, so it won't be caught the same way the errors above are — write `content.config.ts` with `import { defineCollection } from 'astro:content'` and `import { z } from 'astro/zod'` from the start.

Tailwind needs its own explicit treatment, and this is the one place where the exact failure mode has kept shifting release to release rather than settling down, so treat the following as "what to check," not "what's currently true." `@astrojs/tailwind` is deprecated and removed from Astro's own repo. The supported path is Tailwind 4 through the `@tailwindcss/vite` plugin, wired into `vite.plugins` in `astro.config.mjs`, not through `integrations`. Across Astro 6.2.x and the early Astro 7 releases, a rolldown/oxc resolver bug has repeatedly broken one of the two Tailwind integration paths (`@tailwindcss/vite` or the `@tailwindcss/postcss` fallback) while fixing the other, then flipping again on the next Vite bump — so don't assume either path works from a stale report. Before wiring up styling, run a real `npm run build` with a trivial Tailwind-using stylesheet and confirm it actually completes. If `@tailwindcss/vite` fails with an oxc/rolldown resolver error (something like `Missing field 'tsconfigPaths' on BindingViteResolvePluginConfig`), swap to the PostCSS variant: uninstall `@tailwindcss/vite`, install `@tailwindcss/postcss`, and add a `postcss.config.mjs` with `export default { plugins: { '@tailwindcss/postcss': {} } }`. If PostCSS is the one that fails instead, swap back. Check `withastro/astro`'s open issues for the project's exact Astro and Vite versions before picking a side, this bug has moved between the two paths more than once.

One more reserved-field rule is easy to hit while writing this schema from scratch, and it has nothing to do with any specific version. A content collection schema cannot include a field named `slug`. Astro reserves that name for entry-id generation and throws `ContentSchemaContainsSlugError` if it's present. Structure pages still get clean URLs. Generate them from the entry `id`, for example a municipality-plus-name id set by the loader, instead of adding a `slug` field to the Zod schema.

## Repo structure

- `src/pages/` — route files: `index` (home), `map`, `explore` and `explore/[municipality]`, `structures/[id]`, `technical`, `history`, `stories`, `glimpse`, `about`, `404`
- `src/components/` — reusable UI: `Map.tsx` (the one interactive React island; receives every structure's name, municipality, coordinates, classification, facts, thumbnail URL, and a short summary as a build-time prop from the map page, and does not fetch anything itself), `Hero.astro` (the home threshold), `ProvinceModel.astro` and `MapTeaser.astro` (the 3D chipboard model), `MunicipalityArcade.astro`, `Rail.astro` (horizontal rows, no native scrollbar), `StructureCard.astro` (the framed-print card), `PageHeader.astro` (title plus an arched photo window), `RecordIndex.astro` (the Technical Description and History indexes with a scroll-spy municipality list), `Arrow.astro`, `Nav.astro`, `Footer.astro`, and `ScrapbookTemplate.astro` (the structure page body, with History, Feature Story, and Technical Description folder tabs that degrade to stacked sections without JavaScript)
- `src/components/map/boundaries.ts` and `boundaries.svg` — the real 15 Sorsogon municipal boundaries, sourced from PSA's PSGC-based administrative boundary data via faeldon/philippines-json-maps (MIT licensed, itself derived from altcoder/philippines-psgc-shapefiles), already mapshaper-simplified upstream. `boundaries.ts` exports the `BOUNDS` projection box and each municipality's SVG path `d` string, `Map.tsx` imports it directly and renders the paths as interactive elements (hover/focus on a pin highlights its municipality). `boundaries.svg` is a static standalone copy of the same paths for reference or preview outside the component. Both were generated once, not regenerated by any sync script, that Day 1-2 task from earlier drafts of this file is done. If the province's administrative boundaries ever change (a new municipality, a boundary dispute resolution), regenerate both from the same source with the same projection math, don't hand-edit the paths. Credit the source on the map or about page; the about page already does.
- `src/content.config.ts` — Astro content collection schema (Zod, imported from `astro/zod`, not `astro:content`) that the synced structure data must pass (this path, at the `src/` root, is the only supported location as of Astro 6 and later, which is what a fresh scaffold installs by default; `src/content/config.ts` no longer works at all)
- `src/content/structures/` — generated JSON, one file per structure, written by the sync script, not edited by hand
- `scripts/sync-sheet.ts` — fetches the Sheet's publish-to-web CSV export (File > Share > Publish to web on the relevant tab; a public, no-auth URL is the simple default here since the content is meant to be public — see `sosog-tech-plan.md` Section 1). Publish a dedicated `SITE_FEED` tab, not the client's working tabs: their `FOR WEBSITE INPUT` tab has a blank row above its header and different header names, and publish-to-web exposes an entire tab, so a working tab that grows workflow columns (assignee, status, internal remarks) would leak them. `docs/SHEET_SETUP.md` has the exact `SITE_FEED` headers and cell formulas. Also note for later debugging: a published sheet can take a few minutes to a couple of hours to reflect a fresh edit, so an edit made right before the nightly sync fires may not land until the following night. The script validates every row against the schema and writes normalized JSON. Required headers: `name`, `municipality`, `coordinates`, `history`, `technical_description`, `feature_story`. Optional headers, read when present: `year_built`, `classification`, `materials`, `occupancy`, `intervention_level`, `photo`. Two tiers of fields. Structural fields, name, municipality (against a fixed valid list), and coordinates (a single cell of `latitude, longitude` as plain decimal degrees, e.g. `12.9705, 124.0067` — latitude in [-90, 90], longitude in [-180, 180]; reject the two-column split or anything else), must be present and well-formed or the build fails loudly, naming the row and field, since without them there's no pin to place and no page to build. Content fields degrade gracefully instead, each with its own wording: a blank history (an empty cell, or one that holds only N/A) renders "Historical records for this structure are limited." (the team could not find sources for some structures, so this is a permanent state for them, not a placeholder); a blank feature story hides the Feature Story tab and section entirely (feature stories are interviews with local residents and are optional); a blank technical description renders "still being prepared". That tier exists to protect editing after launch, a new structure added before its write-up is finished, an existing one mid-edit, from blocking the nightly deploy for every other structure. Before it processes any row, the script also confirms every required column header is present in the sheet at all. A single row missing a content value is normal, but an entire expected column disappearing (renamed, merged into another cell, deleted) is a structural problem, not a content gap, and fails the whole build loudly by column name instead of quietly blanking that field for every row at once. On a structural failure, the script sends the failure email itself (see Deployment) before exiting non-zero — there's no separate CI step gating the build, so the script's own exit code is what stops a bad deploy, and the script's own network call is what tells anyone it happened.
- `scripts/sosog_prep_photos.py` — a local-only Python tool, not part of the build. It turns a folder of camera originals into `<name>-large.jpg` (1600 px long edge) and `<name>-thumb.jpg` (480 px) with every piece of metadata stripped, and writes a small `manifest.csv` (original name, sizes, capture time, EXIF coordinates when present). The outputs are copied into `public/structures/` (or `public/glimpse/` with `--sequential glimpse`) and committed. Structure photos are matched to structures through the optional `photo` column, which holds the original file name as typed in the sheet (`BULAN SOUTH CENTRAL.png`); `photoKey` in `scripts/lib/validate-row.ts` reduces it to the same stem the script writes (`bulan-south-central`), so renaming a structure never orphans its photo. When `photo` is blank the structure id is used. `src/lib/photos.ts` checks for exactly these file names at build time, and a missing file renders "Photo to be added". Caveat for anyone reading the originals: the GPS Map Camera app prints coordinates on the picture rather than storing them as EXIF, so the manifest's coordinate columns are empty for those photos; they were read from the stamps with OCR instead.
- **No selfies, ever.** The team asked that selfies and posed group photos of themselves stay off the site (the client's Glimpse and home strip included). `GLIMPSE_HIDDEN` in `src/lib/photos.ts` lists the photo numbers that never render (32, 41, 47, 51, plus 18 and 19, which are photographs of prints); the four selfie files were also deleted from `public/glimpse/`. Photo numbers come from `sosog_prep_photos.py --sequential glimpse` and stay fixed, but if a new batch is copied over the folder, look at every new photo for selfies and extend that list before building. Candid shots taken from behind, or with small distant figures, are kept; remove them too if the team asks.
- `public/` — static assets outside the data pipeline: favicon, `structures/` and `glimpse/` (committed photos), and `fonts/` (`maragsa.css`, `Maragsa.woff2`, and the creator's license note; see `public/fonts/README.txt`)
- `wrangler.jsonc` — the main site's Worker configuration: `name`, `compatibility_date`, and an `assets` block pointing `directory` at `./dist` (Astro's static build output, which already includes everything from `public/`). No `main` entry point is needed since this is a pure static-assets Worker with no server-side code.
- `cron-worker/` — a separate, minimal Cloudflare Worker, unrelated to the Astro site and not built by `npm run build`. It has its own `wrangler.jsonc` (`name`, `compatibility_date`, and a `triggers.crons` entry for the nightly schedule) and a small `scheduled()` handler whose only job is `fetch(env.DEPLOY_HOOK_URL, { method: "POST" })`, where `DEPLOY_HOOK_URL` is the main site Worker's Deploy Hook URL, stored as a Worker secret. Deploy this Worker independently of the site (`wrangler deploy` from inside `cron-worker/`); it is the entire nightly-rebuild mechanism, see Deployment below.

## Conventions

Build screen-adaptive: fluid layouts across the full range of screen sizes, not fixed to two breakpoints. Laptop is the primary test target, but keep it mobile-friendly. Every page pulls its content from the build-time content collection, including the map's pin data, which is passed into `Map.tsx` as a build-time prop, not fetched — nothing on the site fetches data client-side. Keep the map's JavaScript isolated to its one component; everything else on the site should ship as plain static HTML. Don't add a new dependency without checking it's actually needed and has no ongoing cost, this project has a hard one-time budget with zero tolerance for surprise subscription costs.

## Commands

- `npm run sync:sheet` — fetch and validate the Google Sheet into content JSON (set `SHEET_CSV_URL`; `sample-data/site_feed.csv` can be served locally for offline work, see README)
- `npm test` — unit tests (row validation, sheet sync, photos, map geometry, grouping helpers, and the map component in a simulated browser); `npm run typecheck` and `npm run check:links` should also pass before anything is pushed
- `npm run validate:data` — schema check only, sharing its structural-field logic with `sync-sheet.ts`; useful to run locally before pushing, but the nightly path no longer runs it as a separate gate, `sync-sheet.ts` does the same check as part of `npm run build` itself
- `npm run dev` — local dev server
- `npm run build` — production build (`dist/`)
- `npm run preview` — preview the production build locally

## Deployment (Cloudflare Workers, static assets)

The site deploys as a Cloudflare Worker connected to the repo through Workers Builds' git integration: push to `main`, Cloudflare detects the build command, runs `npm run build`, and serves `dist/` as static assets per `wrangler.jsonc`. Pin the Node version with a `.node-version` file (22.12.0, or a later even-numbered release like 24.x; the build image's Node default updates periodically, and Workers Builds reads `.node-version`/`.nvmrc` the same way Pages did) instead of relying on whatever default is current at build time. Ships on the free `*.workers.dev` subdomain — no custom domain is being purchased, so there's no recurring registration/renewal cost to plan for after the team graduates. Static asset requests are free and unlimited on every Workers plan, and the free-plan file caps are 20,000 static asset files and 25 MiB per file — comfortably above this project's few hundred files. The build budget on Workers Builds' free plan is 3,000 build minutes a month, one concurrent build, a 20-minute timeout per build — for a small static-site build measured in low single-digit minutes, that's roomier headroom than it sounds and not something a normal 18-day iteration pace will approach.

Sheet URL and the Gmail app password are stored as Workers Builds **build secrets** (Worker > Settings > Build > Variables and secrets), never committed to the repo. Do not use `wrangler secret put` for them: that sets runtime secrets, which the build container cannot read. The cron Worker's `DEPLOY_HOOK_URL` is the one value that does use `wrangler secret put`, because it is read while the Worker runs. There is no Google Drive credential any more, since photos are committed (see the Photos row above).

The repo is public. That buys free secret-scanning push protection on every push — GitHub blocks a push outright if it detects a supported secret pattern (API keys, service account JSON, common token formats) before it reaches the remote, a backstop, not a substitute, for keeping every credential in environment variables and never in the repo. (This is also the only tier at which push protection is free at all: on a personal GitHub account it's a paid add-on for private repos.) There's no GitHub Actions workflow in this design at all, so no scheduled-workflow dormancy rule applies on any platform, this is orthogonal to the Pages-vs-Workers question.

The nightly job is the standalone `cron-worker/` Worker described in Repo structure above: a Cron Trigger firing once a day, whose handler `POST`s to the main site Worker's Deploy Hook. Workers Builds gained Deploy Hooks in April 2026, the identical mechanism Pages has had since 2021, so this part of the design doesn't change shape based on which of the two platforms hosts the site. That single call is the entire mechanism — no GitHub involved, no dormancy clock to defend against, no personal access token to scope or rotate, because there's no second system being remote-controlled. The Deploy Hook URL is itself a bearer credential (anyone who has it can trigger a build), so it's stored as a secret on the cron Worker, never in plaintext, and never in the main site's own secrets (it doesn't need it — only the cron Worker calls it).

Validation happens inside the real build, not as a separate pre-flight step: `sync-sheet.ts` already fails the build loudly on a bad structural field as part of `npm run build`, so a broken row stops the deploy on its own, and the site's previous good version stays live. `sync-sheet.ts` sends the failure email itself (Gmail SMTP, an app password on a 2FA-enabled account created specifically for this project rather than anyone's personal account, since a personal account's password can get changed for unrelated reasons and silently revoke the app password) the moment it detects a structural failure, naming the row and field, and only then exits non-zero. Before this is relied on, send one real test email from an actual build early in the build window — the build container has general outbound network access (the same access that lets `sync-sheet.ts` fetch the Sheet over HTTPS), but whether that access extends to outbound SMTP on port 587/465 is not independently confirmed. This is unrelated to the well-documented restriction that the request-serving Workers runtime cannot make outbound SMTP connections on port 25 — that restriction is about the sandboxed runtime that serves live requests, not the separate build container. If a test email fails to send from a real build, swap the Gmail SMTP call in `sync-sheet.ts` for an HTTP-based transactional email API instead; the build container's HTTPS access isn't in question, so this is a one-function change, not a redesign. If that happens, use Resend's free tier as the fallback. It allows 3,000 emails a month with no card required (capped at 100 emails a day, which is irrelevant here since the only traffic on this address is occasional failure notices), and since this only ever mails the client and dev team, sending from Resend's shared sandbox domain to their pre-verified addresses works without owning a custom domain. Don't reach for Cloudflare's own Email Service here. Outbound sending is still gated behind the Workers Paid plan even now that it's out of beta-adjacent status, a recurring $5 a month cost that conflicts with this project's zero-recurring-cost budget, and Resend's free tier already covers this use case at zero cost. `npm run validate:data` still exists as a shared-logic convenience for running the same check locally before pushing, but it's no longer part of the automated path.

## Known future maintenance item

The Gmail app password behind the failure-notification email is a legacy credential Google is quietly walking away from: basic-auth access to Gmail SMTP is already gone, and app passwords are described in Google's own documentation as a transitional option pushed in favor of OAuth 2.0, with no fixed retirement date. It works today and doesn't need solving yet, but if failure emails silently stop arriving a year from now, this is the first thing to check.

## Changes since the original plan (October 2026)

Decisions made after `sosog-tech-plan.md` was written. Where this list and that plan disagree, this list wins.

- **History and Feature Story are separate fields.** The client first merged them, then asked to hand in History separately and to keep feature stories to interviews with locals. A structure with no history shows "Historical records for this structure are limited."; a structure with no feature story simply has no Feature Story tab.
- **Photos are committed, not synced from Drive.** The Drive service account and `sync-photos.ts` are gone. Use `scripts/sosog_prep_photos.py` for every new batch.
- **Explore follows the guide's sequence:** Explore carousel, then a municipality's structures, then a structure (History tab first). The earlier tap-to-reveal history snippet on explore cards was dropped.
- **Map:** the whole-province view shows small dots only; selecting a municipality raises it, changes its colour, zooms to it, and shows full icons that are spread apart when coordinates coincide (a thin line runs back to the true position). The view widens to include offshore structures such as the San Bernardino Island lighthouse, which lies about 15 km off Bulusan. `/map?s=<structure id>` opens straight to a structure.
- **Palette** (from the guide): maroon `#461717`, cream `#F1EACE`, navy `#2F4461`, ink `#211112`, defined as Tailwind theme tokens in `src/styles/global.css`. The site is dark-themed, matching the guide's typography sample.
- **Typography:** wordmark and headings in Maragsa, installed as a WOFF2 file only (the OTF is deliberately not committed to the public repo; the client's top choice; the guide's typography list still names Para for the title, but Maragsa was chosen). Subheadings and body in Josefin Sans as a free stand-in for Copperplate Gothic.
- **Team emails** may appear on the About page (the team confirmed on 31 October 2026). `SHOW_EMAILS` is on and an email shows once an `email` is added to that member in `src/data/about.ts`; the repo is public, so those emails are public too. The project description there was written from what the site documents.
- **Known data issues** are tracked for the client in `SOSOG_fix_list_for_Micah.xlsx` (wrong or shared coordinates, mislabeled photos, missing years, typos). The site is built to tolerate them: missing photos show a placeholder, shared coordinates are spread apart on the map, and blank years or materials are simply not shown.
- **Audit fixes (October 17, 2026):** `.gitignore` no longer ignores `public/structures/` (it still did from the Drive-sync design, so a first push would have left every structure photo out of the repo); `wrangler.jsonc` sets `assets.not_found_handling` to `404-page` so Cloudflare serves the custom 404 page; build secrets are documented as build secrets, not runtime secrets; feature-story pull quotes no longer cut off at abbreviations such as \"St.\"; and while a map popup is open the view is reframed so the popup does not cover pins.
- **Audit fixes (October 25, 2026):**
  - `isMainModule` (`scripts/lib/is-main.ts`) replaces the `import.meta.url === file://${process.argv[1]}` check in `sync-sheet.ts` and `validate-data.ts`. The old check never matched on Windows or in a folder with a space, so `npm run sync:sheet` silently did nothing and the build reused old JSON.
  - The sync fails when the sheet has the right headers but no structure rows, instead of deleting every structure file and deploying an empty site. Sheet fetches time out after 20 s and retry a 429 or 5xx twice (`scripts/lib/fetch-sheet.ts`); a 404 fails at once. Header names are trimmed, and the build log reports blank fields per field.
  - The map space is 800 wide and `MAP_HEIGHT` (675.39) tall, not 800 x 800. The old square stretched the province about 19% north to south. `boundaries.ts`, `boundaries.svg`, `project()` and the 3D model share it; a test ties `MAP_HEIGHT` to the real east-west to north-south ratio.
  - The History and Technical header figures count what is true (structures with a written history or technical description) instead of every structure. Map, Explore, Stories, Technical and Home wording no longer says content is "yet" to come, "being prepared" or "so far".
  - The Feature Stories deck computed its animation step as `Math.min(0.05, (t - lastT) / 1000 || 0.016)`, which goes negative when a frame's timestamp precedes the click's `performance.now()`. On a slow device that threw the deck toward the first card. `frameSeconds` (`src/lib/motion.ts`) clamps the step to 0 to 0.05 s and has tests.
  - The Glimpse opening no longer scrolls the page sideways on phones (the sun's rays are clipped at the header). The nav plate is a list item, not a bare `span` inside a `ul`. Structure card photos have empty alt text because the link already names the structure.
- **Verification done in the build session:** the unit tests, `typecheck`, `check:links`, and a headless-browser pass over home, explore, map (province, municipality, popup, offshore pin, phone width), structure, and glimpse pages. A person should still look at the site on a real phone and laptop before launch.

## Design system (revised October 18, 2026)

The interface was rebuilt twice after being judged plain, off-palette, and full of stuck-on lines. Keep these rules when adding anything.

- **Palette only, all four colours in play.** Maroon, cream, navy, ink, plus the darker mixes (`maroon-deep`, `navy-deep`) and `maroon-light` for hover and selected states, all defined in `src/styles/global.css`. No other colours. No page may be mostly one colour: the home page runs ink (hero), cream (Explore), maroon (rows), navy (Glimpse), cream (map model), ink (footer). Pages get a dominant wall by role: History maroon, Technical and Map navy, Stories and Glimpse ink, About and Explore cream.
- **Mass, not lines.** Do not add hairline borders, 1px rules, thin outline buttons, dotted leaders, progress hairlines, grid lines, or decorative thin frames. Separate things with solid colour blocks, zebra rows, thick mats, spacing, and weight. Photographs sit in thick cream mats (`.print-frame`), data rows alternate shaded bands, controls are solid blocks.
- **Shape language.** The round arch is the doorway: the hero, the History, Technical, and Glimpse header photo windows, the municipality arcade, the nav plate, and the thumbnail picker. Arches are stepped solid bands (architrave and archivolt), never outlines. Arches are already used a lot, so new pages and sections should reach for something else: square-cornered cream-matted prints, solid colour-block bands, striped rows, folder tabs, and the house-front motifs below. The About page deliberately has no arches.
- **The arrow** is the forged gate spear (`IronArrow.ts`, `Arrow.astro`, `ArrowIcon` in `Map.tsx`): a ball-finial tail, a tapered shaft, a double binding, and a swept head whose barbs end in small balls, drawn as separate solid shapes (never one path with overlapping subpaths, which leaves holes). Use it only on controls that move something: previous and next on rails, the arcade, the story deck, and the photo viewer. Buttons and text links carry no arrows; they are centred text. Do not type `→` and do not put the arrow in a container to make it look themed.
- **Buttons** (`.btn`) are solid centred blocks with a second, offset frame (`outline`) that closes onto the button on hover while a darker block rises behind the label. Use `.btn-sm` for compact ones.
- **Numbers are set in `.figure`** (the body face, lining figures). Maragsa only has old-style numerals, so its 4, 7, and 9 drop below the line and 6 rises; never set digits in Maragsa.
- **No dead space.** Page headers vertically centre the title block against the arched photo and carry intro text and `HeaderStats` so the left column is never a lone title above empty colour.
- **Header is solid ink.** No translucency, blur, or scroll-dependent colour changes anywhere (nav, sticky bars, index lists). The current page is a solid cream arch-topped plate. It is the current link itself (drawn by the server, so it is in place from the first paint) and carries the view-transition name `nav-tab`, so when the page changes the browser carries it from the old tab to the new one while the two labels trade places inside it. The pointer only tints the other links.
- **Wow pieces (keep them working):** the Hero doorway (the page opens on an arched window in a wall, which swings open by itself once per visit into a full-bleed photograph; `--e` runs 0 to 1 and is set in `Hero.astro`; it never ties itself to scrolling, repeat visits in the same session and reduced motion start open, and phones get a static stacked layout); the 3D chipboard province model (`ProvinceModel.astro`, layers in `translateZ`, assembles when scrolled into view, then turns only when dragged, from its turn and reset buttons, or from the arrow keys; nothing follows the pointer around the page); the stepped-block map (`Map.tsx`, documented municipalities stand proud, the selected one is raised higher); the Feature Stories coverflow deck with a grid toggle (`src/pages/stories.astro`); the municipality arcade whose arch under the pointer opens.
- **Wording on the site states only what is known.** Empty states say "No photo available" and "No details recorded", never that something "will be added" or is "coming". The client objected to that assumption.
- **Map details (client feedback, October 23, 2026).** Municipality names on the whole-province map step aside from the dots (`labelSpots` in `Map.tsx`) and are left off if no clear spot exists. The marker popup photo is a full rectangle, not an arch. The home model has no buttons under it; it turns by dragging, arrow keys, or double-click to reset. Feature Story deck cards show only the whole quote lines that fit (`fitQuotes` in `stories.astro`).
- **Motion rules (set by the client, October 2026).** Animation answers an action and stays short and small: hover responses are a few pixels or a tint over about 0.2 to 0.3 s, never a full slide, swap, or slow zoom. Arrows nudge 4 px the way they point and never swap with a second copy. Nothing counts up, loops, or reacts to the pointer unless the pointer is pressing something. Page changes: the old page stays still and the new one fades in over it in 280 ms while rising 10 px (never fade both at once, which dips the page to half brightness midway). Every internal page link ends in a slash (`/map/`, `/structures/<id>/`), because on Cloudflare a link without one costs a redirect on every click; `npm run check:links` fails on any that does not. Pages ask Chromium browsers to prefetch the other pages (speculation rules in `Layout.astro`) and wait for `#main` before the change is shown. The photo viewer on the Glimpse page grows the photo out of its tile while the whole page, header included, dims; on close the photo returns to its tile, which is scrolled into view first if the reader stepped to another photo. A panel that swaps in (a structure page's folder tabs, the map's side panel) fades the old one out, holds the height, then fades the new one in with an 8 px rise, so it never blinks. Check any new animation against this list before adding it.
- **Glimpse of Sorsogon is a road, not a gallery.** The client rejected grids of rectangles and arches rearranged (October 22, 2026) and asked for bespoke work like the About house. The page opens on a sun disc (conic rays, round photo, no arch), then a road winds down the page. `glimpse.astro` measures each stop's sign and draws the road through them as SVG (cream shoulders, ink asphalt, dashes); a top-down jeepney drives along it as the page scrolls. Photos sit on both sides of the road, with the heading alternating sides. The client liked the varied shapes but disliked a messy, uncoordinated look, so shapes follow a system: one shape family per stop (`FAMILY` in `glimpse.astro`: chamfer for Stone, oval for Within, octagon for Along the way, circle for Shore, Light and After dark, step for Small things), fixed proportions per shape, one mat thickness, one solid offset shadow (no CSS filters, which drop images on weak devices), centred captions, and rows that match (one wide print leads a side, then same-orientation pairs). `split()` places prints on the side of the road that balances estimated heights. Keep this system when adding photos. The Light stop has a sun slider that steps through four sunset frames. After dark is a ferris wheel (drag, arrows, arrow keys, or press a cabin; the bottom cabin shows large on the left and opens the viewer). `focus` in `glimpse.ts` sets a photo's crop when its subject is off-centre. Do not return to rectangular grids or arches here. `src/data/glimpse.ts` lists the stops (Stone, Within, Along the way, Shore, Light, After dark, Small things), their wall colours, and each photo's number and caption. Captions say only what the picture shows: no place names, dates, or claims. Photos in the folder but in no chapter appear in a final uncaptioned chapter, so nothing is lost. The viewer shows the caption and chapter name.
- **Motion** answers an action or is one of the pieces above. No scroll-triggered fade-ins. Every animation is off under `prefers-reduced-motion`. Page transitions are native cross-document view transitions (`@view-transition` in `global.css`); the header keeps its own transition name; a structure card morphs into the structure page photo through the `pageswap` handler in `Layout.astro`.
- **Map tests** depend on markup (see `Map.test.ts` before restructuring): province dots are `circle[aria-hidden="true"]` in the province view only, each pin has a non-decorative `circle` as its first circle, the first `svg` in the component is the map, and the `aside` holds the municipality buttons. The "Whole province" button lives in the aside.

- **About page: the house.** The team section is a bahay na bato front built from solid shapes (corrugated hip roof, navy wall, balustrade, ink ground floor). ## Ask before doing

- Adding a new dependency, especially anything with a paid or usage-based tier
- Changing the content schema or the sheet-sync pipeline
- Swapping the map's boundary source, or reaching for a mapping library instead of static SVG
- Changing the deployment target or hosting provider again (this includes moving off Cloudflare Workers, or splitting the site across Workers and Pages — see `sosog-tech-plan.md` Section 3 for why Workers was picked over Pages)
- Building the real wordmark into pages before the exported logo asset is supplied, use the plain text wordmark in the Maragsa font (Maragsa is installed through `public/fonts/maragsa.css`; Georgia is only the fallback)
- Embedding Copperplate Gothic or any other font whose web license is not free. The guide asks for it, but it is a commercial font, so Josefin Sans (open license, self-hosted through `@fontsource`) stands in via the `--font-body` line in `src/styles/global.css`
- Adding team emails to `src/data/about.ts`, or setting `SHOW_EMAILS` to true, before the team confirms their emails may appear on a public site

Note (audit, Sept 2026): `wrangler` was added to the root `package.json` as a devDependency, matching the version already required by `cron-worker/`. This is the one exception to "ask before doing: adding a new dependency" made during that audit — it's a free CLI tool with no usage-based tier, it's already a dependency of `cron-worker/`, and it makes `wrangler.jsonc`'s own `$schema` reference actually resolve locally (it previously pointed at a `node_modules/wrangler/` path that didn't exist at the root). It changes nothing about the deployed site, since Workers Builds runs `npm run build`, not `wrangler` itself.

## Text from the sheet

The three long texts (history, technical description, feature story) are tidied when the sheet is read (`scripts/lib/clean-text.ts`): a line break inside a sentence, as PDFs and Word files leave behind, is joined back; a break after a finished sentence stays as one blank line between paragraphs; stray spaces around punctuation, brackets and quotation marks are removed. No word is ever changed. Fix the source sheet where you can, but the site no longer shows pasted line breaks.
